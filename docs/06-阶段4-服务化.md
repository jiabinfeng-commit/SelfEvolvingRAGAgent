# 阶段 4 服务化：把 RAG 问答包成 HTTP 接口

> 先说清楚一个长期混淆点：**「阶段 4」在项目里其实有两层含义**，别再搞混了。
> - **阶段 4（算法层）**：BM25 混合检索 + RRF 融合 —— 这个在 `core/bm25.py` + `hybrid_retrieve()` 里，**上一轮就已经做完了**，A/B 评估也跑过了（正确率 76%→76%，结论是检索不是瓶颈）。
> - **阶段 4（服务层 / 本次补做）**：把 `ask.py` 那套问答逻辑**暴露成 HTTP 服务**，让前端/其他系统能调。
>
> 本文件讲的是**第二层：服务化**。你之前那句「阶段4的服务化是不是没做」——问得对，确实没做，现在补上。

---

## 一、为什么要服务化（不是为服务化而服务化）

阶段 1~3 的 `ask.py` 只能在命令行跑。每次执行都要：
1. 重新加载 bge embedding 模型（~1s，加载权重 + tokenizer）
2. 重新连 PostgreSQL、重新连 Milvus Lite
3. 重新实例化 LLM 客户端

问题：
- **慢且浪费**：连问 10 个问题 = 重复加载 10 次模型、重连 10 次数据库。
- **不可被调用**：产品/同事想看效果，得开终端敲命令；别的微服务想接 RAG，没门。
- **没法做 UI**：streamlit 页面（阶段 5 那部分）总不能每问一次 `subprocess` 调一遍命令行吧？那是反模式。

服务化之后：
- 模型 + 连接**只在启动时加载一次**，常驻内存，多个请求共享。
- 对外是标准 HTTP 接口，streamlit、curl、任意语言 SDK 都能调。
- 这就是「从脚本到系统」的关键一步 —— 没有服务化，自愈逻辑只能人工触发，谈不上「Agent」。

## 二、架构总览

```
                        ┌─────────────────────────────┐
   浏览器/Postman ──HTTP──▶│  FastAPI (scripts/serve.py) │
   streamlit 页面  ───────▶│                             │
   其他业务系统    ───────▶│  STATE 单例（进程级复用）   │
                        │   emb / pg / vec / llm / bm25│
                        └──────────────┬──────────────┘
                                       │ 调用
                                       ▼
                            core/rag.generate_answer()
                          （与 ask.py / ui.py 同一份逻辑）
                                       │
                 ┌──────────────────────┼──────────────────────┐
                 ▼                      ▼                      ▼
            VecStore(Milvus)      PGStore(PostgreSQL)      LLM(阿里云)
            chunk_id + 向量         chunk 原文 + 元数据       DashScope
```

关键点：**服务层不重新实现问答逻辑**，它只负责「接收 HTTP 请求 → 转交给 `generate_answer()` → 把 dict 序列化成 JSON」。业务逻辑全在 `core/rag.py`，三端（CLI / HTTP / UI）共用，口径永不漂移。

## 三、核心设计：进程单例 + 惰性建引擎

### 3.1 进程单例 `STATE`

```python
STATE = {"emb": None, "pg": None, "vec": None, "llm": None, "bm25": None}
```

整个服务进程只有一个 `STATE`。首次请求时 `ensure_engine()` 把实例填进去，之后所有 `/ask` 复用，**绝不每问一次重建一次**。这是服务化相比命令行最大的性能收益来源。

### 3.2 为什么「惰性建」而不是「启动即建」

很多教程一上来在 `lifespan` 里把 PG、Milvus、模型全连了。问题在于：**存储临时不可达 = 服务直接起不来**。本地开发时 PG 走 SSH 隧道，隧道偶尔断了很正常，结果服务起不来，你还得先去修隧道才能看 Swagger 文档，纯纯的本末倒置。

本项目做法：
- `lifespan` 启动时**只做配置校验**（`config.validate()`）—— 密码/语料缺失这种「真错误」早失败。
- PG / Vec / LLM / BM25 在**首次请求时** `ensure_engine()` 惰性建立并缓存。
- 存储挂了，服务照样能起；`/health` 返回 `status=degraded`（仍 200），`/ask` 真正需要时再报 503。

> 教授吐槽：这不是炫技，是「fail-soft」的基本功。生产环境你要严格启动即校验，把 `ensure_engine()` 挪进 `lifespan` 开头一行就行，代码已经留好位置了。

### 3.3 BM25 索引缓存

阶段 4 算法层的 BM25 索引要从 PG 全量拉 494 块建倒排。建一次约几十毫秒，但**不该每问一次建一次**。所以：
- `serve.py` 在 `ensure_engine()` 里建好 `STATE["bm25"]` 并缓存。
- `generate_answer()` 收到注入的 `bm25` 就直接复用，不重建。
- 注意：**入库新文档后索引会过期**，需要重启服务刷新（demo 阶段完全可接受，生产应改成 PG 的 `tsvector` 全文索引，阶段 4 算法文档里写过）。

## 四、接口详解

### 4.1 `GET /health` —— 健康检查

返回配置摘要 + 存储条数：

```json
{
  "status": "ok",
  "config": {
    "llm_backend": "openai",
    "llm_model": "qwen3.7-max",
    "retrieval_default": "vector",
    "bm25_indexed": true
  },
  "pg":  {"documents": 41, "chunks": 494},
  "milvus": 494
}
```

- `status=ok`：PG 连得上。
- `status=degraded`：PG 连不上（仍返回 200，方便探活脚本区分「活着但存储异常」）。

### 4.2 `POST /ask` —— 问答

请求体（pydantic 自动校验 + 生成文档）：

```json
{
  "question": "FastAPI 怎么做依赖注入？",
  "top_k": 5,
  "retrieval": "vector",        // vector | hybrid
  "self_heal": false,           // 阶段5 自愈开关
  "save": true                  // 是否写 qa_log
}
```

返回（就是 `generate_answer()` 的 dict，FastAPI 自动 JSON 化）：

```json
{
  "question": "FastAPI 怎么做依赖注入？",
  "answer": "FastAPI 中使用 Depends 声明依赖...",
  "retrieved": [
    {"chunk_id": "chunk_xxx", "score": 0.78, "doc_name": "...", "heading": "...", "content": "..."}
  ],
  "latency_s": 3.21,
  "refusal": false,
  "self_healed": false
}
```

- `question` 为空 → **422**（pydantic 字段校验失败，FastAPI 标准行为）
- `retrieval` 不是 vector/hybrid → **400**（代码里显式 `HTTPException(400)`）
- LLM 调不通 / PG 断连 / key 错误 → **503**（不带原始异常栈，前端好处理）

## 五、怎么跑

```bash
# 1) 先开 PG 隧道（你的 .env 里 PG_HOST=localhost，走隧道连云上）
bash scripts/tunnel_pg.sh

# 2) 启动服务（默认 http://127.0.0.1:8000）
.venv/bin/python scripts/serve.py
# 或自定义地址/端口：
.venv/bin/python scripts/serve.py --host 0.0.0.0 --port 8080

# 3) 浏览器打开 http://127.0.0.1:8000/docs  —— FastAPI 自带 Swagger，可网页直接试 /ask
```

试一下：

```bash
curl http://127.0.0.1:8000/health
curl -X POST http://127.0.0.1:8000/ask \
  -H 'Content-Type: application/json' \
  -d '{"question":"FastAPI 怎么做依赖注入？","retrieval":"hybrid","self_heal":true}'
```

| 项目 | 结果 |
| --- | --- |
| 依赖安装 | fastapi 0.141.1 / uvicorn 0.52.4 装好（清华源） |
| 模块导入 | `from core.rag import generate_answer` ✅ |

## 七、生产注意（避坑清单）

1. **别把 8000 暴露公网**：本地开发够用；上云应放反向代理后 + 加鉴权，且 DashScope key 走环境变量不落盘。
2. **并发**：单进程 uvicorn 默认够 demo；真要高并发要加连接池 / 多 worker，并注意 `STATE` 单例在每个 worker 各一份（启动时各自建一次，不影响正确性）。
3. **BM25 过期**：新文档入库后索引不自动刷新，重启服务即可；生产改 PG `tsvector`。
4. **模型配置不动**：`LLM_BACKEND` / `LLM_MODEL` / key 全读 `config.py` + `.env`，服务层零硬编码（阶段 3 起的纪律）。
