# 阶段 2：最小 RAG 闭环（召回 → 拼 Prompt → LLM 生成 → 答案落库）

> 目标：阶段 1 把文档变成「能按意思搜索」的向量库，但还只是个「搜索引擎」。
> 阶段 2 把最后一截补上 —— 用户问一句话，系统召回最相关的几块，交给大模型**基于这些块作答**，再把问答记录存下来。
>
> ```
> 用户问题
>   → bge 编码（带查询前缀，和阶段 1 一致）
>   → Milvus 向量检索 top-k 个 chunk_id（+ 相似度分数）
>   → PG 按 chunk_id 回表拿原文（双存储的"回表"在这步用上）
>   → core/prompt.py 拼成 RAG prompt（上下文 + 问题）
>   → LLM 生成答案
>   → 答案 + 召回信息写入 PG 的 qa_log（"答案落库"）
> ```

---

## 一、为什么需要「闭环」，阶段 1 缺了什么

阶段 1 跑通了 `scripts/search.py`，它能：输入问题 → 召回 top-k → 打印原文块。
但它是**哑的** —— 只是把检索到的原文贴给你，让你自己读、自己总结。

真实 RAG 产品（ChatPDF、各种知识库问答）要的是：**用户问一句人话，系统直接给一句答案**。
这中间缺的「最后一截」就是一句话：

> 把召回的原文块，连同一个明确的指令，一起发给大模型，让模型**只依据这些块**生成答案。

这就是阶段 2 的全部内容。所以阶段 2 不是另起炉灶，而是在阶段 1（切片 + 双存储 + 检索）之上，**加了两样东西**：

1. 一个「拼 prompt + 调 LLM」的链路（`core/llm.py` + `core/prompt.py` + `scripts/ask.py`）
2. 一张「问答日志表」`qa_log`（`core/storage/pg_store.py`），把每次问答存下来

> Java 类比：阶段 1 相当于你写好了 `searchRepository.findByVectorTopK(...)`，能查到数据；
> 阶段 2 相当于你在 Service 层把查到的数据组装成 DTO、调一个外部 `LlmClient.generate()`、再把结果落 `qa_log` 表。
> 模型调用 ≈ 调一个外部微服务（HTTP 请求），不是本地计算。

## 二、闭环的每一步（拿着代码一行行走）

以 `python scripts/ask.py "FastAPI 怎么做依赖注入"` 为例，主流程在 `ask.py:main()`：

| 步骤 | 代码位置 | 干了啥 | 关键细节 |
|---|---|---|---|
| 0 | `ask.py:75` | `config.validate()` 配置校验 | 缺 PG 密码 / LLM 后端非法 → 早失败，不浪费后面时间 |
| 1 | `ask.py:86` | 加载 bge 嵌入模型 | `get_embedder("bge")`，512 维，和阶段 1 同一个模型 |
| 2 | `ask.py:89-93` | 连 PG + Milvus，`pg.init_schema()` | `init_schema()` 含 `qa_log` 建表（`IF NOT EXISTS`，幂等，跑多次不报错）|
| 3 | `ask.py:97` `retrieve()` | 召回 | 见下方「召回」专节 |
| 4 | `ask.py:107` | `build_prompt()` 拼 user 文本 | 见「三、Prompt 怎么拼」 |
| 5 | `ask.py:110` | `--dry-run` 分支 | 到此为止，**不调 LLM、不落库**，只打印 prompt（调试神器）|
| 6 | `ask.py:121-124` | `get_llm().generate(system, user)` | 真正调模型生成答案 |
| 7 | `ask.py:135-139` | 打印答案 + 耗时 | 把答案显示出来 |
| 8 | `ask.py:147` | `pg.save_qa(...)` | 写入 `qa_log`（闭环收尾）|

### 召回这一步（复用了阶段 1 的口径）

`ask.py:retrieve()` 和阶段 1 `search.py` 用的是**同一套逻辑**，故意保持一致，保证「检索口径不变、只加生成」：

```python
def retrieve(question, emb, vec, pg, top_k):
    qv = emb.encode_query(question)        # 加 bge 查询前缀 → 512 维向量（模长 1.0）
    hits = vec.search(qv, top_k=top_k)     # Milvus：[(chunk_id, score), ...]  只有 ID + 分数
    chunk_ids = [cid for cid, _ in hits]
    chunks = pg.get_chunks_by_ids(chunk_ids)   # PG 回表：ID → 原文 + heading + doc_name
    return [(score, chunks[cid]) for cid, score in hits if cid in chunks]
```

注意：Milvus 只吐 `chunk_id` + 分数，**一个字原文都没有**；原文是 PG 给的。这跟阶段 1 第六节的「二级索引回表」完全一致 —— 没变。

## 三、Prompt 怎么拼（抗幻觉的第一道防线）

代码在 `core/prompt.py`。这里最容易写歪：指令不清晰，模型就开始瞎编（幻觉）。
所以本项目把「拼装」单独成一个模块，和「调模型 / 查库」解耦，方便后续调指令、做 few-shot。

### system 指令（`SYSTEM_PROMPT`）

```
你是一个严谨的技术文档问答助手。请只根据下面提供的【上下文】回答用户问题。
规则：
1. 如果【上下文】里找不到答案，请明确回答「根据提供的资料无法回答该问题」，不要编造。
2. 回答尽量简洁、准确，可引用上下文中的要点；不要添加上下文之外的知识。
3. 如上下文相关，可在回答中提及信息来源（如文档章节名）。
```

**为什么要写「无据说不知道」？** 因为 LLM 天生有「讨好用户、硬凑答案」的倾向。
不加以限制，它会在检索内容根本没提到答案时，凭自己训练时的记忆编一段 —— 这在知识库问答里是致命的（答得信誓旦旦但全错）。
这条指令是**抗幻觉的第一道、也是最便宜的一道**防线：免费、零成本、只写一句话。

### user 文本（`build_prompt()`）

把召回的块按相关度从高到低编号 `[资料 1][资料 2]...` 拼进去，每块前标注**来源**（文档名 + 标题路径），方便模型引用、也方便事后溯源：

```
【上下文】
[资料 1] 来源：advanced__dependencies.md / Dependencies
依赖注入是通过 Depends 声明参数，FastAPI 在调用时自动解析。

[资料 2] 来源：advanced__dependencies.md / Dependencies > 类依赖
类级别依赖可对多个依赖共享同一个子依赖实例，减少重复计算。

【问题】
FastAPI 怎么做依赖注入
```

设计要点（都写进注释了）：

1. **编号 + 来源标注**：模型引用时知道「这话出自哪篇文档哪节」，人也方便核对。
2. **单块截断 `RAG_CONTEXT_MAX_CHARS`（默认 1200 字）**：超长块会被截掉尾巴加「…（已截断）」，避免极长块把 prompt 撑爆、还顺带稀释了重点。
3. **纯函数**：`build_prompt()` 不碰数据库、不碰网络，单测即可验证，不依赖外部环境。

## 四、LLM 后端：可插拔（本地免费 / 云端付费）

代码在 `core/llm.py`。设计原则：**业务代码只管「给我 system + user，还我一段文本」，至于用哪家模型、本地还是云端，靠配置切换，不改代码。**

抽象出一个统一接口：

```python
class BaseLLM(ABC):
    @abstractmethod
    def generate(self, system: str, user: str) -> str: ...
```

两个实现 + 一个工厂：

| 后端 | 类 | 端点 | 前提 | 适合场景 |
|---|---|---|---|---|
| `ollama`（默认）| `OllamaLLM` | `POST {OLLAMA_URL}/api/chat` | 本机起了 Ollama + pull 了模型 | 开发期、本地、免费 |
| `openai` | `OpenAILLM` | `POST {OPENAI_BASE_URL}/chat/completions` | 配 `OPENAI_API_KEY` | 上生产、要更强模型、或换 DeepSeek/通义百炼 |

切换方式：改 `.env` 的 `LLM_BACKEND` 和 `LLM_MODEL` 即可，业务代码（`ask.py`）一行不动。

```python
# core/llm.py
def get_llm(backend=None, **kwargs):
    name = backend or config.LLM_BACKEND
    if name == "ollama": return OllamaLLM(**kwargs)
    if name == "openai":  return OpenAILLM(**kwargs)
    raise ValueError(f"未知 LLM_BACKEND: {name}")
```

> **为什么 OpenAI 兼容就能吃 DeepSeek / 通义百炼？** 因为它们都实现了同一套 `/chat/completions` 接口。
> 所以 `OpenAILLM` 配 `OPENAI_BASE_URL=https://api.deepseek.com/v1` + `OPENAI_API_KEY=sk-xxx`，
> 就等于在用 DeepSeek —— 一个类通吃所有「OpenAI 形状」的服务。

### ⚠️ 没引 `requests` 依赖

两个实现都用 **Python 标准库 `urllib.request`** 发 HTTP，没有引 `requests`。
原因：项目一贯保持依赖精简（阶段 1 踩过 `pip` 装包慢且重的坑），发 JSON POST `urllib` 完全够用。
万一中途报 HTTP 错误 / 连不上，`_post_json()` 会转成带详情的 `RuntimeError`，让 `ask.py` 捕获后给清晰提示而不是崩。

```python
# ask.py:123
try:
    answer = backend.generate(SYSTEM_PROMPT, user_prompt)
except RuntimeError as e:
    print(f"\n✗ LLM 调用失败：{e}")
    print("   ollama 后端请确认本机 Ollama 已启动且有对应模型；")
    print("   openai 后端请确认 OPENAI_API_KEY 已配置。")
    sys.exit(1)
```

## 五、答案落库：qa_log 表（闭环收尾，也是阶段 3 的燃料）

代码在 `core/storage/pg_store.py`。每次问答落一条，字段设计是为了**事后能复盘 RAG 效果**：

```sql
CREATE TABLE IF NOT EXISTS qa_log (
    id            SERIAL PRIMARY KEY,
    question      TEXT        NOT NULL,        -- 用户原问题
    answer        TEXT        NOT NULL,        -- 模型生成的答案
    ctx_chunk_ids TEXT[]      NOT NULL DEFAULT '{}',  -- 召回的 chunk_id（按相关度从高到低）
    ctx_scores    REAL[]      NOT NULL DEFAULT '{}',  -- 对应的相似度分数
    model         VARCHAR(64) NOT NULL DEFAULT '',    -- 用了哪个模型
    backend       VARCHAR(20) NOT NULL DEFAULT '',    -- ollama / openai
    latency_s     REAL        DEFAULT 0,             -- LLM 生成耗时（秒）
    created_at    TIMESTAMP   DEFAULT NOW()
);
```

每个字段的用处：

| 字段 | 用处 |
|---|---|
| `question` / `answer` | 问答原文，最基础的对账 |
| `ctx_chunk_ids` | **关键**：记下当时召回了哪些块。答错了能反查「是不是召回就错了」 |
| `ctx_scores` | 召回块的相似度分数。分数低说明召回本身就边缘，答案差不能全怪模型 |
| `model` / `backend` | 换模型做 A/B 实验时区分来源 |
| `latency_s` | 性能基线，上生产看 SLA 用 |

> **为什么这一步很重要？** 阶段 3 要做「Agent 自愈 / 效果评估」，靠的就是 `qa_log` 里这条「问题 → 召回了啥 → 答了啥」的完整链路。
> 现在每问一次就存一次，等于在**自动采集训练/评估数据**。这是「Self-Evolving（自进化）」名字的由来 —— 先有记录，才能复盘、才能优化。
>
> Java 类比：`qa_log` ≈ 一个 `audit_log` / `request_log` 表。线上系统出问题，第一件事就是查日志。RAG 的「日志」就是 qa_log。

## 七、本地 / 云上怎么跑（依赖说明）

阶段 2 比阶段 1 多一个外部依赖：**一个能用的 LLM**。两种来源：

### 本地开发（默认 ollama，免费）

1. 装并启动 Ollama：`ollama run qwen2.5:7b`（首次会拉模型，约 4-5GB）
2. 确认 Ollama 在 `http://localhost:11434` 监听
3. 连 PG：阶段 1 已讲，云 PG 只听 `127.0.0.1`，本地测试要开 SSH 隧道
   ```bash
   ssh -L 5432:127.0.0.1:5432 -N root@你的服务器IP
   # 或直接用仓库里的脚本（需要显式传云主机地址）：
   #   RAG_CLOUD_HOST=root@你的服务器IP bash scripts/tunnel_pg.sh
   ```
   然后 `.env` 里 `PG_HOST=localhost` 即可。也可直接跑本地 PG（Docker 一条命令见 `.env.example`）。
4. 跑：`python scripts/ask.py "你的问题"`

### 云上运行

- 代码已通过 GitHub Deploy key（只读）clone 到 `/opt/rag-agent/app`，`.env` 已还原。
- LLM 后端：云上空跑 Ollama 太吃内存（qwen2.5:7b 约 5-6GB），生产建议 `LLM_BACKEND=openai` 走 API。
- 同样要能连 PG：云上 PG 监听 `127.0.0.1`，Ask 脚本和 PG 同机，直连 `localhost:5432` 即可，无需隧道。

### ⚠️ 没起 Ollama / 没配 key 会怎样

不会崩，会拿到清晰提示：

```
✗ LLM 调用失败：LLM 连接失败（检查服务是否启动/地址是否正确）: [Errno 61] Connection refused
   ollama 后端请确认本机 Ollama 已启动且有对应模型；
   openai 后端请确认 OPENAI_API_KEY 已配置。
```

这正是不引 `requests`、用 `urllib` 自己转 `RuntimeError` 的好处 —— 错误信息人话、可操作。

## 十、踩过的坑（按被坑概率排序）

1. **`SYSTEM_PROMPT` 中文引号导致 SyntaxError** —— 初版用 ASCII 双引号 `"根据提供的资料..."` 包字符串，但字符串里又出现未转义的双引号，Python 直接截断报 `SyntaxError`。
   **解决**：system 指令改用中文引号「」（不会和 Python 字符串界定符冲突），`ask.py --help` 随即通过。**教训**：写含大量引号的中文 prompt 常量，优先用中文引号，别用 ASCII 引号。
2. **`urllib` 不发 `requests`** —— 为保持依赖精简，故意用标准库。代价是错误处理要自己包：`HTTPError` / `URLError` 转成 `RuntimeError` 带详情，否则业务层只会看到一堆堆栈。已封装在 `BaseLLM._post_json()`。
3. **抗幻觉不能只靠 prompt** —— `SYSTEM_PROMPT` 的「无据说不知道」是第一道、最便宜的防线，但不是万能的。召回本身错了（top-k 没召回正确答案），模型再严谨也答不对。所以阶段 3 的重点是**召回质量**（rerank / 混合检索），prompt 只是兜底。
4. **`--dry-run` 必须先于「调 LLM」** —— 调试 prompt 时如果没起 Ollama，直接跑会报连接错。先 `--dry-run` 确认召回和 prompt 对，再真调模型，省时间也省 token。
5. **`qa_log.ctx_chunk_ids` 顺序 = 相关度从高到低** —— `ask.py` 落库时按 `retrieve()` 返回顺序取 `chunk_id`，而 `retrieve()` 返回的是 Milvus 的 score 降序，所以库里存的顺序天然就是「最相关在前」。复盘时直接读第一个 id 就是最关键的块。

## 十一、下一步（阶段 3 前瞻，不实现）

阶段 2 是「最小可用闭环」。它的最大短板是：**召回质量决定天花板，而当前召回只有向量一件事**。
阶段 3 可以接着做（全都能拿 `qa_log` 当评估燃料）：

- **Rerank**：召回 top-20 → 用交叉编码器重排 → 取 top-5 进 prompt，缓解「向量召回准但排不对」
- **混合检索**：向量（语义）+ BM25（关键词）融合，cover 专业术语
- **评估集自动打分**：用 `eval/` 里的问题，批量跑 `ask.py --no-save`，拿答案和 gold 比，出端到端准确率
- **Agent 自愈（项目名来源）**：答错 / 低分时，自动反思「是召回错了还是 prompt 错了」，调检索或重问
