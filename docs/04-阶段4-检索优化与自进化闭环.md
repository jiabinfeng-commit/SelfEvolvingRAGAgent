# 阶段 4：检索优化（BM25 混合检索）与自进化闭环

> 目标：阶段 3 把「答得对不对」量化了。阶段 4 就干两件事：
> **① 修掉向量检索的短板（加 BM25 关键词召回）→ ② 用阶段 3 的评估闭环验证它真的变好了。**
>
> ```
> 召回 = 向量语义(top20) ┐
>                        ├─ RRF 融合 → top_k → 拼 prompt → LLM → 裁判打分 → eval_run
> 召回 = BM25 关键词(top20)┘
> ```
>
> 这两步合起来就是「**测量 → 优化 → 再测量**」的自进化闭环：
> 没有阶段 3 的评估，这一步的优化就是盲调；没有这一步的优化，阶段 3 的评估就只是个仪表盘。

---

## 一、为什么要混合检索（向量检索到底短在哪）

阶段 1~3 只有一条召回链路：**bge 向量语义检索**。它很强（懂同义改写、懂语义），但有两个硬伤：

| 场景 | 向量检索的表现 | 原因 |
|---|---|---|
| 问「`Depends` 怎么用」 | 可能召回一堆"依赖"相关内容，但**不含 `Depends` 这个词** | 语义相近 ≠ 字符串匹配 |
| 问「`HTTPSRedirectMiddleware` 参数」 | 容易被"HTTPS 配置""中间件"等主题带跑 | 长尾专有名词在向量空间里区分度低 |

**BM25**（Elasticsearch / Lucene 的默认打分算法）正好相反：它做的是**精确的关键词匹配**，
"Depends" 就是 "Depends"，不会给你"依赖注入"的近似语义。

两者互补：
- **向量**：懂语义（"怎么让接口依赖别的东西" → 能找到"依赖注入"）
- **BM25**：懂字面（"Depends" → 只找含这个词的块）

混合之后，通常比单用任一个都稳。这就是工业界 Hybrid Search 成为 RAG 标配的原因。

> Java 类比：向量检索 ≈ Lucene 的「语义/模糊搜索」，BM25 ≈ Lucene 的「倒排索引精确打分」。
> ES 之所以又稳又准，就是因为它把两者都做了。我们这里用 40 行 Python 复刻了这个思路。

## 二、BM25 原理（含公式）

代码在 `core/bm25.py`，**纯 Python、零新增依赖**。

### 打分公式

对查询里的每个词 `t`、文档 `d`：

$$\text{score}(t, d) = \text{IDF}(t) \times \frac{tf \times (k_1 + 1)}{tf + k_1 \times (1 - b + b \times \frac{dl}{avgdl})}$$

| 符号 | 含义 | 直觉 |
|---|---|---|
| `IDF(t)` | $\ln\left(1 + \frac{N - df(t) + 0.5}{df(t) + 0.5}\right)$ | **越稀有的词权重越高**（"的"不值钱，"Depends"很值钱）|
| `tf` | 词 t 在文档 d 里出现次数 | 出现越多越相关（但会饱和，见下）|
| `dl` / `avgdl` | 文档长度 / 全库平均长度 | **长文档不该因为词多就赢**，所以有长度惩罚 |
| `k1=1.5` | 词频饱和参数 | tf 从 1→2 提升大，从 10→11 几乎没提升 |
| `b=0.75` | 长度惩罚强度 | b=0 完全不惩罚长度，b=1 惩罚拉满 |

### 中文分词：不用 jieba，用 bigram

没有引入 jieba（保持依赖精简），中文按**字 bigram 滑动切分**：

```
"依赖注入" → ["依赖", "赖注", "注入"]
```

这是中文信息检索里最经典、无依赖且效果不错的做法：既保留了词序信息，
又不需要词典。ASCII 部分按正则切成词（`fastapi`、`pydantic.settings` 整体保留）。

实测分词效果：
```
tokenize("FastAPI 依赖注入 Depends")
→ ['fastapi', 'depends', '依赖', '赖注', '注入']
```

### 为什么不装 rank_bm25 / jieba？

项目一贯保持依赖精简（阶段 1 就用标准库 `urllib` 替代了 `requests`）。
BM25 公式本身很短，494 块的规模纯 Python 完全够用，还顺手建了**倒排索引**
（词 → 文档列表），查询时只遍历命中查询词的文档，不会退化成全库扫描。

## 三、RRF 融合：为什么用「排名」而不是「分数」

两条链路各自召回 top-20，怎么合并成最终 top-5？用 **RRF（Reciprocal Rank Fusion，倒数排名融合）**：

$$\text{fused}(d) = \sum_{\text{各召回列表}} \frac{1}{k + \text{rank}_{\text{list}}(d)}$$

即：把候选块在**每条召回列表里的排名**换算成分数再加总（k=60 是论文经典取值）。

### ⚠️ 关键：为什么不能直接把两路分数加权相加？

因为**量纲完全不同**：
- 向量分是余弦相似度，范围 ~0~1
- BM25 分是无上界的实数（实测能到 2~10+）

直接 `0.5*cosine + 0.5*bm25`，BM25 的数值大小会把结果完全带跑偏，
权重怎么调都是在调"数值尺度"而不是"重要性"。

**换成排名就没有量纲问题**——第 1 名就是第 1 名，不管你原始分是 0.9 还是 10.0。
这就是 RRF 的全部智慧，也是它成为混合检索事实标准的原因。

### 融合效果（离线单测验证）

```
向量返回：[("c2", 0.9), ("c1", 0.5)]     ← 向量认为 c2 最像
BM25 返回：[("c1", 10.0), ("c3", 5.0)]   ← 关键词认为 c1 最像

RRF 融合后 top-2：['c1', 'c2']
```
`c1` 在**两条链路都出现**，所以融合分最高被顶到第一 —— 这正是我们想要的：
"两边都觉得对"的块应该排最前。

## 五、自进化闭环：两次 run 直接比数字

`eval_run` 表把每次评估的指标都存下来了，`note` 里记了检索方式。所以验证优化效果就是一句 SQL：

```sql
SELECT id, n_questions, accuracy, partial_rate, refusal_rate,
       recall_top1, recall_top3, avg_latency_s, note
FROM eval_run ORDER BY id;
```

这就是「自进化」的落地形态：**每次改动都用同一套评估跑一遍，看数字涨跌，而不是凭感觉**。
后面要做 rerank、换 embedding、调 chunk 大小，全都是这个套路。

## 六、A/B 对比结果（真实数字）

> 环境：本地 + PG 隧道（494 chunk），LLM = 阿里云 `qwen3.7-max`（openai 兼容），
> 评测集 50 题，两轮**同一套题、同一个裁判、只换召回方式**。

| 指标 | vector（基线, run 3）| hybrid（阶段4, run 4）| 变化 |
|---|---|---|---|
| 题数 | 50 | 50 | — |
| **正确率**（裁判=2）| 76.0%（38/50）| 76.0%（38/50）| **±0.0pp** |
| 部分正确率（裁判=1）| 12.0%（6/50）| 16.0%（8/50）| **+4.0pp** |
| 完全错误（裁判=0）| 6 题 | **4 题** | **−2 题** |
| 拒答正确率 | 100.0% | 100.0% | ±0.0pp |
| recall@1 | 66.0% | 66.0% | ±0.0pp |
| recall@3 | 74.0% | 74.0% | ±0.0pp |
| 耗时/题 | 15.16s | 15.95s | +0.79s |

hybrid 各题型 recall@3：`single_hop 88.9%`(36题) / `multi_hop 83.3%`(6题) / `unanswerable 0%`(8题，本来就该拒答)

### 结论 1：混合检索在本数据集上 ≈ 中性（没拉高准确率）

**诚实结论**：换混合检索后准确率一动没动（76% → 76%），召回率也完全一样。
按「准确率」这个主指标看，**这次优化没有带来提升**。

为什么？三个原因：
1. **语料小且同质**：494 块全是 FastAPI 官方文档，词汇分布集中，
   BM25 找到的块和向量找到的高度重叠 → 融合后 top-5 基本没变（recall@1/@3 完全一致就是证据）。
2. **题目偏语义、不偏关键词**：评测集多是「为什么…」「如何…」这类描述性问题，
   向量本来就擅长；BM25 的精确匹配优势发挥不出来。
3. **recall 不是当前瓶颈**（见结论 2）。

### 结论 2：它确实减少「完全错误」（6 → 4 题）

虽然准确率没动，但**「完全答错」从 6 题降到 4 题**，这 2 题被抬到了「部分正确」。
说明混合召回让上下文稍微更全了一点，模型不至于完全跑偏 —— 这是一个**小但真实的质量改善**，
只是没强到能把答案抬进「完全正确」。

### 结论 3（最有价值）：评估帮我们定位了「真正的瓶颈不在检索」

看逐题明细，#40、#42 的失败模式是：

```
[错误] #42 FastAPI 应用返回数据无效时会发生什么
       recall_top3=✓          ← 正确文档明明召回到了！
       理由: 待评审回答直接表示无法回答，完全未覆盖参考答案核心要点
```

**召回是中的（recall_top3=✓），但模型选择了「拒答」** ——
说明阶段 2 那句抗幻觉指令「无据说不知道」被**过度触发**了：
上下文其实有答案，模型却判成"资料不足"直接拒答。

也就是说：**当前瓶颈已经从「检索」转移到了「生成/拒答策略」**。
如果不做评估，我们会继续在检索上加码（rerank、混合、扩召回），
但真实收益点其实在生成侧 —— 这正是「先测量再优化」的价值：
**它告诉你下一步该改哪里，而不是让你凭直觉瞎调。**

### 下一步建议（按评估结论，而不是按直觉）

1. **调生成侧**：给拒答加一个"置信度阈值"，或改成「先尝试作答，确实没有再说不知道」，
   解决 over-refusal（预计能直接把 #40/#42 这类题救回来）。
2. 上 **rerank**：现在 top-5 里可能混了边缘块稀释重点，重排能把真正相关的顶到最前。
3. 每一步改完都跑一遍 `evaluate.py`，跟 run 3/4 的数字比 —— 这就是自进化闭环。

## 七、踩过的坑

1. **RRF 必须用排名，不能用原始分** —— 向量分(0~1) 和 BM25 分(无上界) 量纲不同，
   直接加权相加会被 BM25 的数值尺度带跑偏。这是混合检索最容易写错的地方。
2. **中文分词别依赖 jieba** —— 多一个依赖就多一份维护成本；`bigram` 对中文检索足够好，
   而且是零依赖方案。注意单字片段要保留（否则 "的" 这类单字被丢，影响很小但会漏）。
3. **BM25 索引要建在"全量 chunk"上** —— 用 `pg.get_all_chunks()` 一次拉全量（494 块）。
   生产环境块数很大时，应换成数据库侧全文索引（PG 的 `tsvector`），别再全量拉内存。
4. **评估很费时间/token** —— 50 题 × 2 次 LLM 调用（生成 + 裁判）≈ 13 分钟。
   所以调参阶段务必先 `--limit 5/10` 快速试，确认方向对了再跑全量。
5. **拒答率要在同一套题上比** —— 8 道 unanswerable 题单独算 `refusal_rate`，
   它和 `accuracy` 是两回事：拒答率下降往往意味着幻觉变多，不能只看准确率。

## 八、与阶段 3 的衔接

- 阶段 3 是**测量**（judge 打分 + eval_run 落库）
- 阶段 4 是**优化 + 用测量验证优化**（BM25 混合 + A/B 对比）

`run_evaluation()` 加一个 `bm25` 参数就把两件事串起来了：
**同一个评估器、同一套题，只换召回方式，数字直接可比** —— 没有比这更干净的 A/B 了。

## 九、阶段 5 前瞻（都靠这套闭环验证）

- **Rerank 精排**：召回 top-50 → 交叉编码器/LLM 重排 → top-5 进 prompt。
  BM25 只能补"字面"，rerank 能补"精细相关性"。
- **换 embedding / 调 chunk 策略**：改完跑同一套评估比 `recall_top3`。
- **Agent 自愈**（项目名里 "Self-Evolving" 的终极形态）：
  答错（`judge_score=0`）或低召回时，自动换检索策略重试 —— 触发条件就是阶段 3 的分数。
- 每一步都遵循：**改 → 跑 `evaluate.py` → 比 `eval_run` 数字**。
