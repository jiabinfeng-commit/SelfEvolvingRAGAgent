# 阶段 7：知识库体检 Agent（自动找出"该修的内容"）

## 一句话

知识库跑久了会悄悄积累垃圾（过时/矛盾/僵尸/重复）。阶段 7 做一个"体检 Agent"，
跑四个检测器，产出一份**人能直接照着处理**的 Markdown 健康报告。

> 体检 Agent **只读不写**：报告只给建议（合并/更新/删除），绝不自动改库。
> 真要动数据（尤其删 chunk）必须人来拍板——避免 Agent 自己删库的灾难。

## 四个检测器

| 检测器 | 检测什么 | 怎么判定 | 是否需要 LLM | 严重度 |
|---|---|---|---|---|
| `detect_stale` 过时 | 内容已过期 | 正则扫"最新/当前版本"等时效词 + ① 提到旧年份(≤当前年-2) 或 ② 文档入库>365天 | 否（纯规则） | medium/low |
| `detect_conflicts` 矛盾 | 同文档内两段打架 | 同 `doc_name` 的 chunk 两两交给 LLM 判"是否冲突" | **是** | high |
| `detect_zombies` 僵尸 | 入库却从没被召回 | 从 `qa_log.ctx_chunk_ids` 反推"召回过的集合"，全库 chunk 减去它 | 否（查 PG） | low |
| `detect_duplicates` 重复 | 高度相似内容 | 重编码全库 chunk，余弦 ≥ 0.95 的聚成一簇 | 否（纯向量） | medium |

### 设计取舍（和项目纪律一致）

1. **可注入 / 可跳过**：矛盾检测要烧 LLM，`llm=None` 时自动跳过并在报告里注明；
   其余三个纯规则/纯向量，无 LLM 也能跑。
2. **僵尸不引新表**：复用 `qa_log` 已经记的 `ctx_chunk_ids`（每次问答召回了哪些块），
   展开成集合就是"曾经被用到过"的块。这比专门开 `chunk_hit_log` 表省事，但有个前提——
   线上问答要 `save=True`（默认）才会写 `qa_log`；若一直 `--no-save`，会得到空集，
   体检会误报"全是僵尸"，文档/CLI 都已注明。
3. **重复阈值定 0.95 这么高**：bge 归一化后，同义改写通常 0.7~0.85，真正"几乎一字不差"
   才到 0.95+。定太高可能漏（非精确重复不报），定太低会误报（同主题不同内容）。
   0.95 = "几乎重复才报"的保守线，符合"宁可漏报也不乱删"。
4. **矛盾只做文档内**：跨文档矛盾理论上也要查，但成本太高（N²×LLM）。先做文档内，
   已覆盖绝大多数"前后矛盾"场景；跨文档可后续按 embedding 聚类再细查。

## 模块 API（core/health_check.py）

```python
# 四个独立检测器（输入都是普通数据结构，便于单测注入桩）
detect_stale(chunks_with_doc, use_llm=False, llm=None, current_year=None) -> List[HealthIssue]
detect_conflicts(chunks_with_doc, llm=None, max_pairs=200) -> List[HealthIssue]   # llm=None → 跳过
detect_zombies(pg, chunks_with_doc=None) -> List[HealthIssue]
detect_duplicates(chunks, emb, threshold=0.95) -> List[HealthIssue]

# 总入口：跑全套 + 生成 Markdown
run_health_check(pg=None, vec=None, emb=None, llm=None, *,
                 dup_threshold=0.95, stale_days=365,
                 max_conflict_pairs=200, use_llm_stale=False,
                 report_path=None) -> {
    "issues": [HealthIssue...],
    "summary": {documents, chunks, total_issues, by_kind, by_severity},
    "staging_docs": [...],     # 阶段6 写入、待人工转 active 的影子库
    "markdown": str,           # 可直接落盘的 Markdown 报告
    "skipped": [str...],       # 因缺依赖被跳过的检测器说明
}
```

`HealthIssue` 字段：`issue_id / kind / severity / chunk_ids / doc_ids / doc_names / detail / suggestion`。

## 运行入口

```bash
python scripts/health_check.py                      # 全套，报告写 health_report.md
python scripts/health_check.py --report out.md      # 指定路径
python scripts/health_check.py --no-conflict        # 跳过矛盾检测（省 LLM）
python scripts/health_check.py --dup-threshold 0.97 # 调重复阈值
python scripts/health_check.py --print              # 报告同时打印到终端
```

## 指标 / 产出数据

- `summary.by_kind` / `by_severity`：各类问题计数，可纵向对比"体检越来越干净"。
- `staging_docs`：阶段 6 自动补的内容待人工转正，是"防投毒最后一公里"的抓手。
- 后续可把每次体检的 `summary` 落库（仿 `eval_run`），做"知识库健康度随时间"的曲线。

## 已知限制

- 矛盾检测只做文档内、且依赖 LLM 判断质量（可能漏跨文档矛盾、可能误判）。
- 僵尸检测依赖 `qa_log` 是否被填充（一直 `--no-save` 会误报）。
- 过时检测是启发式，可能漏"没写年份但其实已过时"的内容（如"配置见附录"类）。
- 体检只读不写：删除/更新动作仍需人工在 `scripts/ingest.py` / PG 客户端执行。
