# 阶段 3：端到端评估闭环（自进化系统的「度量」）

> 目标：把「答得对不对」量化成可对比的数字。
>
> ```
> 评测集每题 → 召回(复用阶段2) → 拼 prompt(复用阶段2) → LLM 生成答案(复用阶段2)
>          → LLM 当裁判打分(0/1/2) → 聚合指标 → 写 eval_run/eval_result → 出报告
> ```

---

## 一、为什么必须有「评估」（不自测就瞎优化）

阶段 1 证明了「能搜」，阶段 2 证明了「能答」。但「答得对不对」一直没量化。
阶段 3 干的事就是用 **LLM 当裁判（LLM-as-judge）** 对每道题自动打分，把模糊的「感觉还行」变成硬指标。

三个理由，缺一个都不行：

### 1. RAG 的真理：答案质量 ≤ 召回质量
你后面要改检索（rerank / 混合）、改 prompt、换模型——到底变好还是变坏？
**没有稳定指标，所有「优化」都是盲调**。eval_run 表把每次跑分存下来，下次优化直接 `SELECT` 两次 run 的 `accuracy` / `recall_top3` 比高低。

### 2. 这是「Self-Evolving（自进化）」的地基
项目名里的「自进化」= 系统能根据反馈自己变好。反馈从哪来？就是评估分数。
没有评估，就没有反馈信号，所谓自进化是空中楼阁。

### 3. 拒答能力也要测
评测集里 8 道 `unanswerable`（语料里真没有答案）。答这些题「正确」的行为是**拒答**，
答错（编造）是最严重的幻觉。评估专门给拒答题一套打分标尺，把「幻觉率」也量出来。

> Java 类比：相当于上线前的**回归测试 + 准确率指标**。你改完检索逻辑，
> CI 跑一遍 `evaluate.py`，accuracy 掉了就立刻知道——而不是靠肉眼翻答案。

## 二、闭环每一步（拿着代码走）

以 `python scripts/evaluate.py --limit 3` 为例，主流程在 `evaluate.py:main()` + `evaluator.py:run_evaluation()`：

| 步骤 | 代码位置 | 干了啥 | 说明 |
|---|---|---|---|
| 1 | `evaluate.py` `load_questions` | 读 `eval/questions.json` | 40 题，含 `gold_answer`/`gold_doc`/`type` |
| 2 | `evaluator.run_evaluation` `retrieve` | 召回 top-k 块 | **复用 `core/retrieval.retrieve`**，和阶段 2 同一口径 |
| 3 | `build_prompt` | 拼 user（上下文+问题）| **复用阶段 2 的 prompt**，保证测的是线上真实链路 |
| 4 | `llm.generate(SYSTEM_PROMPT, user)` | 生成答案 | **复用阶段 2 的同一调用**，用一个后端（现阿里云）|
| 5 | `grade_answer` | LLM 当裁判打分 0/1/2 | 阶段 3 新增① |
| 6 | 聚合 `summary` | 算 accuracy/recall/拒答率 | 阶段 3 新增② |
| 7 | `pg.save_eval` | 写 `eval_run`+`eval_result` | 阶段 3 新增③（落库对比）|
| 8 | `render_md` | 出 Markdown 报告 | 方便存档 / 发 wiki |

**关键点**：步骤 2/3/4 与阶段 2 `ask.py` 用的是**同一套函数**，阶段 3 只多出「裁判 + 聚合 + 落 eval 表」。
所以评估测的就是线上真实链路，不是另一个平行实现——这保证了指标可信。

## 三、裁判怎么打分（LLM-as-judge）

代码在 `core/evaluator.py`。设计成两套标尺，因为「可答题」和「拒答题」的「正确」定义相反：

### 可答题（single_hop / multi_hop）
拿 `问题 + 标准答案(gold_answer) + 模型答案`，让裁判判：
- `2 = 正确`：准确覆盖参考答案核心要点，无编造
- `1 = 部分正确`：方向对但遗漏要点，或表述含糊但不算错
- `0 = 错误`：关键事实错 / 编造了参考答案没有的信息 / 答非所问

### 拒答题（unanswerable）
语料本就没有答案，正确行为是「拒答」。让裁判判：
- `2 = 正确拒答`：明确说明根据提供的资料无法回答
- `1 = 含糊`：模棱两可，既没明确拒答也没明确编造
- `0 = 幻觉`：给了一个具体答案（编造），最严重

裁判 prompt 片段（可答题）：
```
【题型】可答题
【问题】FastAPI 类是从哪个类继承而来的？
【参考答案】FastAPI 是直接继承自 Starlette 的类……
【待评审回答】<模型生成的答案>
请按 0/1/2 打分并给出一句中文理由，严格只输出如下格式：
分数: <0|1|2>
理由: <一句话>
```

### 容错（重要）
裁判返回可能多嘴，用正则 `_parse_judge` 只抽「分数: X」和「理由: Y」。抽不到分数就记 `0 + 原因`，
**整轮评估不会因为一道题裁判抽风就崩**。

| `core/evaluator.py` | **新**：`JUDGE_SYSTEM_PROMPT` + `build_judge_prompt` + `grade_answer` + `run_evaluation`（生成+裁判+聚合）| 新 |

| `scripts/ask.py` | `retrieve` 改为 `from core.retrieval import retrieve`（DRY，删掉本地副本）| 改（不破坏阶段 2）|

### 用法

```bash
python scripts/evaluate.py --limit 5     # 先跑 5 题自测（快、省 token）
python scripts/evaluate.py               # 全量 40 题评估
python scripts/evaluate.py --no-save      # 跑但不写 eval 表（只打印+报告）
python scripts/evaluate.py --output my_report.md
```

| 参数 | 作用 |
|---|---|
| `--limit N` | 只跑前 N 题，自测/省钱用 |
| `--top-k N` | 召回块数（默认读 `RAG_TOP_K=5`）|
| `--no-save` | 跑但不写 `eval_run`/`eval_result` |
| `--output` | 报告输出路径（默认 `eval/report_<run_id>.md`）|

## 五、eval 表 schema（自进化横向对比用）

```sql
CREATE TABLE eval_run (           -- 每次跑评估一条汇总
    id SERIAL PRIMARY KEY,
    created_at TIMESTAMP DEFAULT NOW(),
    model VARCHAR(64), backend VARCHAR(20), top_k INTEGER,
    n_questions INTEGER,
    accuracy REAL,          -- 正确率(裁判=2)
    partial_rate REAL,      -- 部分正确率(裁判=1)
    refusal_rate REAL,      -- 拒答正确率(仅 unanswerable 题)
    recall_top1 REAL, recall_top3 REAL,   -- 检索命中率
    avg_latency_s REAL,
    note TEXT
);

CREATE TABLE eval_result (        -- 每题一条明细
    id SERIAL PRIMARY KEY,
    run_id INTEGER REFERENCES eval_run(id) ON DELETE CASCADE,
    qid INTEGER, question TEXT, qtype VARCHAR(20),
    gold_doc VARCHAR(255), generated TEXT,
    judge_score INTEGER, judge_label VARCHAR(20), judge_reason TEXT,
    recall_top1 BOOLEAN, recall_top3 BOOLEAN, latency_s REAL
);
```

以后要对比「优化前 vs 优化后」：
```sql
SELECT id, created_at, accuracy, recall_top3, refusal_rate
FROM eval_run ORDER BY id DESC LIMIT 10;
```

## 七、踩过的坑（按被坑概率排序）

1. **DashScope 401：RAM AccessKey ≠ DashScope API Key**（本次实跑卡点）
   兼容端点 `/compatible-mode/v1` 要的 `Authorization: Bearer <key>` 是 **DashScope API Key**
   （在 Model Studio / 百炼控制台单独申请的 key）。`.env` 里填的 `id:secret` 是阿里云 **RAM AccessKey**，
   两者不是一回事，拿来当 Bearer 直接 401。换成 DashScope API Key 即可。

2. **`LLM_MODEL` 要 DashScope 模型 id**
   DashScope 不认 Ollama 标签（如 `qwen2.5:7b`）。要用 `qwen-plus` / `qwen-max` / `qwen2.5-7b-instruct` 等。
   修好 key 后若报 `model not found (404)`，就是模型 id 不对（这个也归「模型配置」，按你要求我不动）。

3. **ask.py / evaluate.py 的 retrieve 重复 → 抽到 `core/retrieval.py`**
   原本三处各写一份召回，维护易飘移。抽到公共模块后，阶段 2 重构为 `import` 复用，`--help` 通过，
   保证「检索口径」永远一致（以后加 rerank 只改一处）。

4. **裁判返回格式容错**
   `_parse_judge` 用正则抽 `分数: X`，抽不到记 `0 + 原因`，整轮不崩。

5. **评估对 LLM 失败整体容错**
   生成答案挂了 → `generated="(生成失败: ...)"`；裁判挂了 → `(0,'错误','裁判调用失败: ...')`。
   单题失败不影响其他题，最后仍能出汇总和报告。

## 八、与阶段 1/2 的衔接

- 阶段 1：切片 + 双存储（能搜）
- 阶段 2：召回 → 拼 prompt → LLM 生成 → 落 `qa_log`（能答）
- 阶段 3：在阶段 2 的真实链路上加「裁判打分 + 指标聚合 + 落 `eval` 表」（能量化答得对不对）

生成答案这一步三者完全复用，阶段 3 不动生成逻辑，只叠加评测。这是刻意的：
**评估必须测线上真实链路，指标才有意义**。
