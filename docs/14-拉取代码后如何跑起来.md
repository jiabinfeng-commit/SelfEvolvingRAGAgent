# 拉取代码后如何跑起来（新人上手 / 换机器手册）

> 本文回答一个很具体的问题：**别人 clone 了这个仓库，能直接跑吗？**
> 答案：**不能。** 但缺的东西很少、很好补，按本文走一遍通常 10~20 分钟能跑起来。
>
> 相关文档：`docs/13-项目完整介绍与操作手册.md`（项目全貌与功能详解）、
> `README.md` 第五节（精简版）、`requirements.txt`（依赖清单）。

---

## 1. 结论先行：为什么不能直接跑

git 仓库里**只有代码和语料**，下面这些是**故意不入库**的：

| 不在仓库里 | 本地体积 | 为什么不入库 | 补齐方式 |
| --- | --- | --- | --- |
| `models/BAAI__bge-small-zh-v1.5/` | **183MB** | 模型权重不适合进 git | `python scripts/fetch_model.py` |
| `data/milvus.db` | 4.2MB | 运行时产物，可从 PG 重建 | **一般不用管**；想有数据就 `python scripts/ingest.py` |
| `.env` | — | **含真实密码** | `cp .env.example .env` 再填 |
| `.venv/` | 1.4GB | 依赖装在本地 | `pip install -r requirements.txt` |
| `frontend/node_modules/` | 195MB | 同上 | `cd frontend && npm install` |
| `frontend/dist/` | 1.3MB | 构建产物 | 开发用 `npm run dev`；部署才 `npm run build` |

**已经在仓库里、不用你管的**：

| 已在仓库 | 说明 |
| --- | --- |
| `corpus/clean/`（41 篇 FastAPI 中文文档） | ✅ 语料直接可用，**离线也能入库**，不需要重新爬 |
| `eval/questions.json`（50 条评测题） | ✅ 可直接跑评估 |
| 全部源码 / 文档 / 前端工程 | ✅ |

所以新人**唯一必须自己弄的是**：Python 依赖、embedding 模型、一个 PostgreSQL、一个 `.env`。

## 3. 最短路径（一条命令）

```bash
git clone <仓库地址> && cd Self_Evolving_RAG_Agent
bash scripts/setup_new_machine.sh
```

这个脚本会自动做完：

```
[1/6] 检查环境（python3 / node / docker）
[2/6] 建 .venv 虚拟环境
[3/6] 装 requirements.txt（默认走清华源）
[4/6] 从 ModelScope 下 embedding 模型（183MB）
[5/6] 用 Docker 起本地 PostgreSQL（容器 rag-pg）
[6/6] 生成 .env + 跑配置自检
```

可用环境变量覆盖行为：

```bash
RAG_PG_PASSWORD=mypass bash scripts/setup_new_machine.sh   # 自定义 PG 密码（默认 rag_dev）
PYTHON_BIN=python3.12 bash scripts/setup_new_machine.sh    # 指定 python 解释器
SKIP_PG=1 bash scripts/setup_new_machine.sh                # 跳过起 PG（你已有 PG）
PIP_INDEX=https://pypi.org/simple/ bash scripts/setup_new_machine.sh   # 换 pip 源
```

> **它不会做的事**（刻意的）：
> ① 不覆盖已存在的 `.env`；② 不自动入库；③ 不帮你配 LLM。
> 原因：这三件事都需要你本人确认，自动化反而容易把已有的正确配置搞坏。

## 4. 手把手（想搞清每一步就按这个来）

### 4.1 Python 依赖

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple/
```

> ⚠ **`torch` 是最大的坑**：它由 `sentence-transformers` 连带安装，
> **Linux 上 pip 默认给的是 CUDA 版（2~3GB）**。只用 CPU 的话先手动装 CPU 版能省 90% 时间——
> 具体命令写在 `requirements.txt` 的头注释里。
>
> 顺带一提：**上传 PDF / DOCX 需要额外的 `pdfplumber` / `python-docx`**，
> 它们已在 `requirements.txt` 里（标了"可选"）。没装也不影响启动，只是上传这两种格式时会报带安装提示的错误。

### 4.2 embedding 模型

```bash
.venv/bin/python scripts/fetch_model.py
# → models/BAAI__bge-small-zh-v1.5/（约 183MB）
```

走 **ModelScope**（国内直连可用，不需要翻墙）。不要试图从 huggingface.co 下，国内不通。

`core/config.py` 会自动检测：本地有这个目录就用本地路径，否则退回 HF 官方 id。

### 4.3 PostgreSQL

**方案 A：Docker（推荐）**

```bash
docker run -d --name rag-pg -p 5432:5432 \
  -e POSTGRES_USER=rag -e POSTGRES_PASSWORD=rag_dev -e POSTGRES_DB=rag \
  postgres:16
```

**方案 B：你已经有 PostgreSQL**

新建一个库和用户即可：

```bash
createuser -P rag      # 记下密码
createdb -O rag rag
```

**建表不用手动做**：`PGStore.init_schema()` 是幂等的（全部 `CREATE TABLE IF NOT EXISTS`），
后端首次请求时会自动建。

> **不需要**手动起 Milvus 服务。本项目用的是 **Milvus Lite**（嵌入式），
> 数据就是一个本地目录 `data/milvus.db`，`pymilvus` 会自动拉起。目录不存在时会自动创建。

### 4.4 `.env`

```bash
cp .env.example .env
```

必需改的：

```ini
PG_PASSWORD=你要的密码        # ← 必填，缺了启动直接 fail-fast
```

然后 **LLM 二选一**（见 §5）。

### 4.5 入库

```bash
.venv/bin/python scripts/ingest.py
```

把 `corpus/clean/` 的 41 篇文档切片 → 向量化 → 写 PG + Milvus。
**首次会加载 bge 模型（十几秒到几十秒），之后再跑就快了。**

> 这一步是**幂等**的：`doc_id = md5(文件名)`，重复跑是覆盖而不是追加，不会产生重复数据。

### 4.6 起服务

```bash
# 终端 1：后端
.venv/bin/python scripts/api.py                # → http://127.0.0.1:8000/docs

# 终端 2：前端
cd frontend && npm install && npm run dev      # → http://127.0.0.1:5173
```

## 5. LLM 配置（二选一，必做）

不配的话：**上传 / 检索 / 体检都能用，但"问答"会返回 503**。

### 方案 A：云 API（推荐，快）

```ini
LLM_BACKEND=openai
LLM_MODEL=qwen3.7-max
OPENAI_API_KEY=sk-你的key
OPENAI_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1   # 阿里云百炼
```

只要兼容 OpenAI 协议，任何端点都行（DeepSeek、硅基流动、自建 vLLM…），换 `OPENAI_BASE_URL` + `LLM_MODEL` 即可。

### 方案 B：本地 Ollama（完全免费）

```bash
# 先装 Ollama（https://ollama.com），然后：
ollama pull qwen2.5:7b
```

```ini
LLM_BACKEND=ollama
LLM_MODEL=qwen2.5:7b
OLLAMA_URL=http://localhost:11434
```

> 注意：项目里的**阶段 6 缺口自愈**会联网调研（走 DuckDuckGo HTML，纯标准库 urllib，免 Key），
> 部分网络环境会被限流；失败会优雅降级（不抛异常、不入库），不影响其他功能。

## 6. 跑起来后的验证清单

按顺序打勾，任何一步不对都能立刻定位：

| # | 命令 | 期望结果 | 不对时看 |
| --- | --- | --- | --- |
| 1 | `.venv/bin/python -c "from core import config; print(config.validate())"` | `[]`（空列表） | 报错信息会直接说缺什么 |
| 2 | `curl localhost:8000/api/health` | `{"status":"ok",...}` | `degraded` = PG 没通，核对 `.env` 的 `PG_PASSWORD` |
| 3 | `curl localhost:8000/api/stats` | documents=41 / chunks 有数字 | 数字是 0 = 没入库，回去跑 §4.5 |
| 4 | `curl "localhost:8000/api/jobs"` | `{"jobs":[],"total":0}` | 404 = 后端版本旧，拉最新代码 |
| 5 | 打开 `localhost:8000/docs` | Swagger 列出 14 个接口 | — |
| 6 | 打开 `localhost:5173` | 顶栏状态灯绿色 `● 在线` | 黄色"降级" = 看第 2 步 |
| 7 | 在「检索测试」页输入 `FastAPI 怎么做依赖注入？` | 召回若干块 + 分数 | 召回为空 = 没入库/入库失败 |
| 8 | 在「问答」页问同一句 | 得到答案 + 可展开的召回块 | 503 = LLM 没配好，回 §5 |

## 7. 三种常见场景

### 场景 A：全新机器 / 别人 clone（最常见）

按 §3 或 §4 走一遍即可。**不需要**作者的任何云端资源。

### 场景 B：想把作者本地的环境整个搬过来

作者本地有 `models/` 和 `data/milvus.db`，但**它们没进 git**，所以别人 clone 拿不到。

**推荐做法：不要搬，重新生成。** 因为：

1. 向量库和 embedding 模型是**强绑定**的——`milvus.db` 里的向量是用特定模型（bge-small-zh-v1.5, 512 维）算出来的。
   如果你的模型版本/维度不一致，检索出的结果会毫无意义（而且**不会报错**，这是最可怕的）。
2. `corpus/clean/` 已在仓库里，重新入库只要几分钟，比传输 + 校验更省事、更可靠。
3. Milvus Lite 的 `milvus.db` 是**目录**（不是单文件），跨版本复制有兼容风险。

**如果实在要搬**（比如语料是你私有的、不在仓库里）：

```bash
# 模型（183MB）
scp -r 对方:项目路径/models            ./
# 向量库（整个目录）
scp -r 对方:项目路径/data/milvus.db    ./data/
```

搬完**必须确认两件事**：

```bash
# ① 维度对得上
.venv/bin/python -c "from core import config; print('EMBED_DIM =', config.EMBED_DIM); print('模型 =', config.EMBED_MODEL)"
# ② 向量数对得上（应等于 chunks 数）
curl localhost:8000/api/stats
```

维度不一致 → 删掉 `data/milvus.db` 重新入库，别硬凑。

### 场景 C：项目里哪些变了要重新入库？

| 变了什么 | 要不要重新入库 |
| --- | --- |
| 改了 `corpus/clean/` 里的文档 | ✅ 要（跑 `scripts/ingest.py`） |
| 换了 embedding 模型 / 改了 `EMBED_DIM` | ✅ 要，**且必须先删 `data/milvus.db`**（维度变了无法复用） |
| 改了切片策略 | ✅ 要（同一文件会被覆盖更新） |
| 只改了 prompt / 检索参数 | ❌ 不用 |
| 只改了前端 | ❌ 不用 |

## 8. 新人常见报错速查

| 报错 | 原因 | 解决 |
| --- | --- | --- |
| `ModuleNotFoundError: No module named 'core'` | 不在项目根目录执行 | `cd` 到项目根再跑 |
| `No module named 'psycopg2'` 等 | 依赖没装 / 装到了别的 Python | 确认用的是 `.venv/bin/python`，并装了 `requirements.txt` |
| `Form data requires "python-multipart" to be installed` | 少了 `python-multipart` | `pip install python-multipart`（已在 requirements.txt） |
| `PG_PASSWORD 未设置` | `.env` 没填密码 | 填 `.env`，注意 `.env` 要在项目根 |
| `语料目录不存在` | `corpus/clean/` 被删了 | `git checkout -- corpus/` 恢复 |
| `/api/health` 返回 `degraded` | PG 连不上 | 核对 `PG_HOST/PG_PORT/PG_PASSWORD`；Docker 容器起来没（`docker ps`） |
| 问答返回 503 | LLM 没配 | 见 §5；Ollama 起了没、API Key 对不对 |
| 检索召回为空但 stats 有数字 | 向量库集合是 released / 换了进程 | 重启后端；代码里 `ensure_loaded()` 会自动 load |
| `Collection is in state 'released'` | Milvus 进程结束会回到 released | 代码已自动处理；自写脚本要记得调 `ensure_loaded()` |
| 上传 PDF 报 `读取 PDF 需要 pdfplumber` | 没装可选依赖 | `pip install pdfplumber`（DOCX 同理装 `python-docx`） |
| 上传后进度条卡在「加载模型」 | 首次加载 bge 模型，正常 | 等十几秒到几十秒；一直不动看后端控制台 |
| `pip install torch` 慢到怀疑人生 | 在下 CUDA 版（2~3GB） | 见 `requirements.txt` 头注释的 CPU 版装法 |
| 下模型卡住 | huggingface 国内不通 | 用 `scripts/fetch_model.py`（走 ModelScope） |

## 9. 附：为什么不把 `models/` 和 `data/` 提交进 git？

常见的疑问是"我把这两个目录提交上去，别人不就能直接跑了吗？"——不建议，理由：

1. **体积**：模型 183MB + 向量库 4.2MB，塞进普通 git 会让每次 clone 都变慢，而且 git 会**永久保留**这些大对象的每个版本，仓库会越滚越大。
2. **强绑定风险**：向量库里的向量是由特定 embedding 模型产出的。别人拿到你的 `milvus.db` 却用了别的模型（或不同版本），检索会**静默出错**——不报错，但结果全错。这比"多跑一步入库"危险得多。
3. **可再生产**：`corpus/clean/` 已在仓库里，别人跑一次 `scripts/ingest.py` 就能得到**和他自己模型完全匹配**的向量库。这一步是幂等的、离线的、几分钟的。
4. **密码卫生**：`data/` 和 `.env` 一起忽略，能避免误把凭据推上去。

**如果你确实要分发大数据**（比如语料是私有数据集），正确做法是：

| 需求 | 正确工具 |
| --- | --- |
| 分发大模型权重 / 向量库 | **Git LFS**（`git lfs track "models/**"`）或 GitHub Release 附件 |
| 分发私有语料 | 私有对象存储（S3/OSS）+ 下载脚本，或 ModelScope / HuggingFace 数据集仓库 |
| 只要别人能跑 | **什么都别传**，让别人跑 `fetch_model.py` + `ingest.py`（本项目采用的方案） |
