# 阶段 1：文档切片 + 双存储入库

> 目标：把一堆散装文档，变成「能按意思搜索」的形式，然后存好。
>
> ```
> 文档 → 切成小块(chunk) → 每块转成 512 个数字(向量) → 数字和原文分两处存好
> ```

---

## 一、为什么要切块

三个理由，缺一个都不行：

### 1. 语义会被「平均」掉
一个 512 维向量装不下整篇文档的全部意思。把 5000 字压成一个向量，等于把 10 个主题搅成一锅粥 ——
搜什么都能沾点边，搜什么都不够准。

> Java 类比：不用 `Files.readAllBytes()` 读 2GB 文件，得分块 `BufferedReader` 读。
> 区别是：Java 分块为了内存，RAG 分块为了**语义精度**。

### 2. 用户要的是「那一段」，不是「那一篇」
问「怎么做依赖注入」，给整篇 `tutorial__dependencies__index.md`（3000 字）让人自己找？
还是直接给讲依赖注入的那 300 字？

### 3. LLM 上下文窗口是花钱的
阶段 2 要把召回内容塞进 prompt。塞 3 个 chunk（约 1000 字）和塞 3 篇文档（约 9000 字），
成本和速度差一个数量级。

---

## 二、两种切法

| 策略 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| `fixed` | 固定 512 字，重叠 64 字 | 简单，长度可控 | 会把一个主题从中间劈开 |
| `structural`（默认） | 按 `#` / `##` / `###` 标题层级切 | 一个 chunk = 一个完整主题 | 块长不均，超长要再切 |

本项目用 `structural`。它还会生成**面包屑标题**，例如：

```
heading = "部署概念 > 安全性 - HTTPS > HTTPS 示例工具"
```

这个字段后面有大用：给 LLM 提供上下文、做元数据过滤、展示引用来源。

## 三、Chunk 长什么样（真实数据）

以 `deployment__concepts.md` 第 2 块为例：

```python
{
    "chunk_id":    "75e0b2aaf3eda1e2",
    "doc_id":      "02142d0665b42fd4",
    "heading":     "部署概念 > 安全性 - HTTPS",
    "char_start":  505,
    "char_end":    674,
    "chunk_index": 1,
    "content":     "## 安全性 - HTTPS\n\n在上一章有关 HTTPS 中，我们了解了 HTTPS 如何为你的 API 提供加密。……"
}
```

每个字段的用处：

| 字段 | 用处 |
|---|---|
| `chunk_id` | 向量的主键，Milvus 与 PG 靠它关联 |
| `doc_id` | 反查属于哪篇文档；删除文档时批量删向量 |
| `heading` | 面包屑上下文，可给 LLM / 做过滤 |
| `char_start` / `char_end` | 定位到原文位置，前端可做高亮 |
| `chunk_index` | 保持块在文档内的顺序（后面做上下文扩展要用）|

## 四、文本 → 512 个数字

查询 `"FastAPI 怎么做依赖注入"` 编码后的向量，前 8 维：

```
[-0.0891, 0.0147, 0.0062, -0.0552, -0.0100, 0.0292, -0.0461, 0.0048]
```

**千万别问「第 3 维是什么意思」** —— 没有意思。单个维度人类无法解释。
有意义的是**整体方向**：意思相近的文本，向量指向相近的方向。

### ⚠️ Java 人必踩的坑：这不是 hashCode

| | Java `hashCode()` | Embedding 向量 |
|---|---|---|
| 设计目标 | **故意打散**（改一个字符，值天差地别）| **故意聚拢**（意思相近，向量相近）|
| 方向 | 雪崩 | 聚合 |

一个是故意打散，一个是故意聚拢，方向完全相反。

### 余弦相似度

$$\cos(\theta) = \frac{A \cdot B}{|A| \times |B|}$$

入库时已把所有向量**归一化**（模长 = 1.0），所以分母没了：

$$\cos(\theta) = A \cdot B = \sum_{i=1}^{512} A_i \times B_i$$

**就是 512 次乘法再累加**，没有任何魔法。

### 真实打分

查询：「FastAPI 怎么做依赖注入」

| chunk | heading | 余弦相似度 |
|---|---|---|
| ✅ 正确 | 依赖项 | **0.7591** |
| ❌ | 部署概念 | 0.5682 |
| ❌ | 部署概念 > HTTPS 示例工具 | 0.4610 |
| ❌ | 部署概念 > 安全性 - HTTPS | 0.4441 |

差距 0.7591 vs 0.4441 —— 这就是检索能不能命中的关键。

## 五、为什么分两个库（设计核心）

| | **PostgreSQL** | **Milvus Lite** |
|---|---|---|
| 存什么 | 原文、标题、位置、元数据 | 只有 `chunk_id` + 512 个浮点数 |
| 擅长 | 精确查询、条件过滤、事务、可修改 | 向量相似度计算 |
| 检索中的角色 | 被 ID 点名查数据 | 在全库里找最像的 |
| Java 类比 | MySQL / JPA Repository | Lucene 倒排索引 |

### 不让 Milvus 也存原文的四个理由

1. **元数据过滤是 SQL 的强项** —— 「只搜 2026 年后的文档」一句 `WHERE` 搞定，向量库做这个又慢又别扭
2. **原文要能改** —— 改个错别字 `UPDATE` 一行，不用动向量
3. **大字段拖慢检索** —— 向量库核心操作是「494 条向量挨个比」，每条挂 2KB 原文是找不痛快
4. **一套原文配多套向量** —— 阶段 3 做模型对比实验时，原文只存一份，向量库可开多个集合

## 六、检索时两家怎么配合

以 `"FastAPI 怎么做依赖注入"` 为例：

| 步骤 | 谁干 | 干什么 | 输出 |
|---|---|---|---|
| 1 | `embedder.py` | 查询加 bge 前缀 → 编码 | 512 维向量，模长 1.0 |
| 2 | `vec_store.py` | Milvus 在 494 条里找最像的 5 条 | `[("a1b2...", 0.7591), ...]` **只有 ID 和分数** |
| 3 | `pg_store.py` | 拿这 5 个 ID 回 PG 查原文 | 原文 + heading + 文件名 |
| 4 | `search.py` | 按分数排序拼装 | 展示 |
| — | — | 全程耗时 | **0.07 秒** |

**关键**：Milvus 只告诉你「这 5 个 ID 最像」，它一个字原文都没有。原文是 PG 给的。

> **Java 类比**：跟 MySQL 的**二级索引回表**一模一样。
> 二级索引树里只有「索引列 + 主键」，查到主键后回聚簇索引拿整行。
> Milvus ≈ 二级索引，PG ≈ 聚簇索引。

## 七、Milvus Lite 不是「数据库服务」

常见误解：以为要起一个向量数据库服务。**不需要。**

| | Milvus Lite（本项目）| Milvus Standalone（生产）|
|---|---|---|
| 形态 | 一个 pip 包 + 一个 `milvus.db` 文件 | Docker 容器组（milvus + etcd + minio）|
| 类比 | **SQLite** | MySQL Server |
| 要不要起服务 | 不需要 | 需要，监听 19530 |
| 内存 | 极小 | 约 8GB |

**同一套 pymilvus API**，切换只改一行 uri：

```python
MilvusClient(uri="./milvus.db")            # Lite
MilvusClient(uri="http://host:19530")      # Standalone
```

## 十、踩过的坑（按被坑概率排序）

1. **`os.getenv("X", default)` 空串陷阱** —— 环境变量设了但为空时不返回 default，
   dotenv 解析 `KEY=` 会设成空串。解决：写 `_get()` 把「空串」和「未设」一视同仁。
2. **Milvus 集合 released** —— 进程结束后集合回到 released，新进程检索前必须 `load_collection()`，
   否则报 `Collection is in state 'released'`。
3. **Milvus Lite 不建父目录** —— 要自己 `os.makedirs`。
4. **pymilvus 3.x 主键是 `.id`** —— `hit["id"]` 会 KeyError。
5. **slice 丢内容** —— 标题行只写进 heading 没写进正文，覆盖率 85% → 99.3%。
6. **国内 ECS 访问 HF 不通** —— huggingface.co 和 hf-mirror.com 都返回 000，走 ModelScope。
7. **pip 装 torch 极慢** —— 默认拉 CUDA 版 2-3GB，用 curl 直下阿里云 CPU wheel（176MB / 13 秒）。
